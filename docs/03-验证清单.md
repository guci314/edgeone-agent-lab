## 第 2 步 · 【未知数 1】后台执行能力 ⭐ 最关键

在状态页点「**跑一次自测**」按钮。它做两件事：

1. `POST /feishu?probe=start` → 立刻返回，后台睡 15 秒后写标记
2. 等 16 秒 → `POST /feishu?probe=check` → 读标记

**预期结果 A（✅ 后台可用）**：

```json
{
  "phase": "finished",
  "verdict": "✅ 后台执行可用 —— 用默认的 FEISHU_DISPATCH_MODE=async"
}
```

→ `FEISHU_DISPATCH_MODE` 保持 `async`。

**预期结果 B（❌ 后台不可用）**：

```json
{
  "phase": "started",
  "verdict": "❌ 后台任务没跑完（响应发出后进程被回收了）—— 把 FEISHU_DISPATCH_MODE 改成 sync"
}
```

→ 把 `FEISHU_DISPATCH_MODE` 改成 `sync`，重新部署。

**为什么要 15 秒**：太短的话任务可能在响应发出之前就跑完了，测出来的是
「同步能跑」而不是「后台能跑」—— 假的通过。

命令行等价做法：

```bash
CID=probe-abc123

curl --noproxy '*' -s -X POST "http://localhost:8088/feishu?probe=start" \
  -H "Makers-Conversation-Id: $CID"

sleep 16

curl --noproxy '*' -s -X POST "http://localhost:8088/feishu?probe=check" \
  -H "Makers-Conversation-Id: $CID"
```

**先确认 `.env` 里没配 `FEISHU_ENCRYPT_KEY`**（不配就跳过验签，好测）。

```bash

  -H 'content-type: application/json' \
  -d '{
    "header": { "event_type": "im.message.receive_v1", "token": "你配的-VERIFICATION-TOKEN" },
    "event": {
      "sender": { "sender_type": "user", "sender_id": { "open_id": "ou_test" } },
      "message": {
        "message_id": "om_test_1",
        "chat_id": "oc_0123456789abcdef0123456789abcdef",
        "chat_type": "p2p",
        "message_type": "text",
        "content": "{\"text\":\"/help\"}"
      }
    }
  }'
```

**预期**：

- webhook 返回 `{"code":0}`
- 控制台里看到 agent 收到转发
- 发消息那一步会失败（`tenant_access_token` 取不到，除非凭证是对的）——
  **这是正常的**，本地没有真实飞书应用时本来就发不出去

**这一步验证的是**：检查顺序对不对、conversation_id 有没有生成成功、
转发链路通不通。不是验证「消息能不能发到飞书」。

### 顺手验一下那个 36 字符的坑

```bash
# 上面的 chat_id 是 35 字符，拼 fs- 会变 38 —— 看 webhook 是否仍然返回 200
# 如果 agent 返回 400，说明 conversation_id 生成那一步没走哈希
```

看 agent 的响应（webhook 失败时会带上 `detail`）：应该是 `{"ok":true,...}`，
不是 `{"error":"缺少 Makers-Conversation-Id 请求头"}`。

## 第 5 步 · 真实飞书链路

1. 配好 `FEISHU_ENCRYPT_KEY`（现在该配上了）
2. 按 `docs/02-飞书配置.md` 走完飞书后台配置，**记得发版本**
3. 私聊 bot：

| 发什么 | 预期 |
|---|---|
| `/help` | 收到命令列表 |
| `/status` | 「还没有导入仓库。发 `/repo owner/name` …」 |
| `/repo sindresorhus/is-stream` | 先「正在抓取 …」，再「已导入 …N 个文件」 |
| `/status` | 显示仓库名、文件数、语料大小 |
| `这个包是怎么判断一个对象是不是 stream 的？` | 基于实际代码回答，带 `路径:行号` |
| 再发一次**同样**的问题 | 正常回答（不同 message_id，不该被去重） |
| `/compact` | 「已压缩：N 条历史 → 摘要（约 M 字）」 |
| 压缩后问 `我们刚才聊了什么` | **能从摘要答出**（这条是压缩的关键验收：答不出说明写回的形状不对） |
| `/clear` | 「会话已清空…」 |
| 清空后问 `我们聊过什么` | 回答没有历史；但 `/status` 里**仓库还在** |
| 空会话上发 `/compact` | 「只有 N 项历史，没什么可压缩的」 |

4. **验去重**：在飞书后台的推送日志里点「重新推送」同一条消息 ——
   bot 不该再回答一次。

5. **验自环防护**：bot 发「正在抓取…」这类回执时，
   那条回执自己会作为事件推回来 —— 不该触发新一轮对话。

## 第 6 步 · 部署

推到 Git 仓库让 Makers 自动构建，或：

```bash
npm run deploy
```

⚠️ **两个部署的坑（都实测踩过）**：

1. **`deploy` 后面不要带路径参数**。`edgeone makers deploy .` 会跳过本地构建、
   把整个源码目录直接打包上传，平台侧重装依赖再构建，产物很容易超过
   「单文件 25MiB」限制（实测 30MiB 被拒）。`npm run deploy` 不带路径，
   CLI 会本地构建进 `.edgeone/` 并只上传构建产物（平台日志显示
   `Project only contains .edgeone directory, skipping build` 才是对的）。
2. **部署前删掉项目根的 `edgeone-agent-lab.zip`**。CLI 部署时会在项目根生成
   这个打包 zip，而它的静态资源收集不认识 `.zip`（默认只排除
   `node_modules/.cache/.git/.DS_Store/*.log/*.tmp`），下一轮构建会把它当
   静态文件收进 `.edgeone/assets/` → 31MiB 超限，从此每次部署都失败。
   `npm run deploy` 已把 `clean:zip` 串在前面。

**部署后要重跑第 2 步**（`https://<域名>/feishu?probe=start` / `?check`）——
线上的实例回收策略可能和本地不一样，本地通过不代表线上通过。

## 一张表：出问题先看哪

| 现象 | 去哪看 |
|---|---|
| 类型错误 | 第 0 步的 `npm run typecheck` |
| 路由 404 | 文件位置：`agents/feishu/index.ts` → `/feishu`，`cloud-functions/feishu-webhook/index.ts` → `/feishu-webhook` |
| 401 内部令牌不匹配 | `INTERNAL_TOKEN` 在 webhook 和 agent 两边是不是同一个 |
| 503 没有配置 INTERNAL_TOKEN | 环境变量没配。这是**故意的** fail-closed |
| 400 缺少 Makers-Conversation-Id | webhook 的转发头没带上，或直接访问了 `/feishu` |
| 飞书收不到任何回复 | 第 5 步的排错顺序表 |
| 回答和仓库无关 | 语料没导入成功 —— 发 `/status` 看文件数 |
| 卡片一直停在「生成中」 | 卡片权限没配，或 `closeStreaming` 失败。`streamer.finish()` 里已吞掉异常，不影响已显示的内容 |
