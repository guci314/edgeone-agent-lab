# 02 · 飞书后台配置

目标：让飞书把消息事件送到 agent，并允许 bot 回消息。

前置：有一个飞书**自建应用**（[open.feishu.cn](https://open.feishu.cn/app) → 创建企业自建应用）。

---

## 0. 当前的链路：CF Worker 转发（本机零依赖）

⚠️ 链路改过两次，**当前生效的是第三种**：

| 版本 | 链路 | 结局 |
|---|---|---|
| v1 | 飞书 → EdgeOne cloud-functions 转发 | ❌ 平台不支持自环（404 domain endpoints match fail） |
| v2 | 飞书 → 长连接 → 本机 bridge 进程 | ✅ 能用，但**依赖本机开机**，已弃用 |
| **v3（当前）** | 飞书 → **CF Worker**（agent.yujizi.org）→ EdgeOne agent | ✅ 免费常驻，本机关机照常用 |

```
飞书 ──webhook──> agent.yujizi.org/api/feishu/edgeone（cf-agent-lab 里的转发路由）
                      │  验签/解密 → 立即 ACK → ctx.waitUntil 后台转发（带重试）
                      └──HTTP──> https://eolab.yujizi.org/feishu（EdgeOne agents 路由）
                                     └── agent 跑模型，自己调飞书 API 回复
```

- 转发层代码在 **cf-agent-lab** 仓库：`src/feishu/edgeone-relay.ts`。
  密钥走它的 wrangler secret（`EO_BOT_VERIFICATION_TOKEN` / `EO_BOT_ENCRYPT_KEY` /
  `EO_INTERNAL_TOKEN`），目标地址在 wrangler.jsonc 的 vars（`EO_AGENT_URL`）。
- `bridge/` 目录是 v2 的遗迹，**留作备选**（如果哪天 CF 不想用了，本机跑起来就能顶上）。
- 改了 `EO_*` 密钥后要 `wrangler secret put` + 重新部署 CF，再同步到 EdgeOne
  侧的 `INTERNAL_TOKEN`（两边必须同值）。

后台里对应这两处（应用 →「事件与回调」→「事件配置」）：

| 配置项 | 值 |
|---|---|
| 订阅方式 | **将事件发送至开发者服务器** |
| 请求地址 | `https://agent.yujizi.org/api/feishu/edgeone` |
| 已添加事件 | 接收消息 `im.message.receive_v1` |

## 1. 拿三样东西

进入应用 → 「凭证与基础信息」：

| 拿到什么 | 配到哪 |
|---|---|
| `App ID`（`cli_` 开头） | 环境变量 `FEISHU_APP_ID` |
| `App Secret` | 环境变量 `FEISHU_APP_SECRET` |

进入应用 → 「事件与回调」→「加密策略」：

| 拿到什么 | 配到哪 | 说明 |
|---|---|---|
| `Verification Token` | `FEISHU_VERIFICATION_TOKEN` | 明文 token，用于比对事件来源 |
| `Encrypt Key` | `FEISHU_ENCRYPT_KEY` | **建议配** |

> **为什么建议配 Encrypt Key**：不配它就没有任何请求来源证明 ——
> 只靠明文比对 Verification Token，谁都能伪造事件推送（`src/feishu/crypto.ts`
> 的文件头写了这一条）。配了之后每个事件都带 `X-Lark-Signature`，
> 由 `verifyToken + timestamp + nonce + body` 算出，能证明是飞书发的。

⚠️ **本地调试时可以先不配 Encrypt Key**：不配的话验签那一步整个跳过，
发一条明文 JSON 就能测通链路。等链路通了再配上、重新部署。

## 2. 开权限

进入应用 → 「权限管理」，搜索并开通：

| 权限 | 用途 |
|---|---|
| `im:message` | 读消息（接收事件必需） |
| `im:message:send_as_bot` | 以应用身份发消息 |
| `im:message.p2p_msg:readonly` | 单聊消息读取 |
| `im:message.group_msg` | 群聊消息读取（只做单聊可以不配） |

**云文档（读 + 写，2026-09-25 起读写都要）**：

| 权限 | 用途 |
|---|---|
| `docx:document:readonly` + `docx:document` | 新版文档读 + 追加正文 |
| `wiki:wiki:readonly` | 知识库链接解引用 |
| `bitable:app:readonly` + `bitable:app` | 多维表格读 + 写记录 |
| `sheets:spreadsheet:readonly` + `sheets:spreadsheet` | 电子表格读 + 写单元格 |

> 这些权限**同时服务两种身份**：应用身份（tenant token，读共享给机器人的文档，
> 用户无需授权）和用户身份（/login OAuth）。改完权限要发一个新版本才生效；
> 已经 /login 过的用户要重新授权一次才会拿到新加的写 scope。

**卡片权限（可选，配了才有流式打字机效果）**：

| 权限 | 用途 |
|---|---|
| `cardkit:card:write` | 创建/更新流式卡片 |

> 不配卡片权限不会影响可用性 —— `src/feishu/streamer.ts` 的 `start()` 会返回
> false，自动退回「攒完整段再发一条纯文本」。流式是体验，不是正确性。

---

## 3. 配事件订阅

进入应用 → 「事件与回调」→「事件配置」：

1. **订阅方式** 选「**将事件发送至开发者服务器**」
2. **请求地址** 填：

   ```
   https://<你的 Makers 域名>/feishu-webhook
   ```

   本地调试填内网穿透地址（`ngrok` / `cloudflared` 之类），飞书要求 HTTPS。

3. 点「保存」—— 这一步会**立刻**发起一次 `url_verification` 握手。

   > ⚠️ 如果飞书后台报「Challenge code没有返回」，八成不是你的代码问题，
   > 而是签名校验顺序错了。`cloud-functions/feishu-webhook/index.ts` 里
   > 挑战握手**不做签名校验**且排在验签之前 —— 飞书文档原文说安全校验
   > 「不包括请求网址校验」。这一步的凭据是 Verification Token，不是签名。

4. 添加事件：搜索 `接收消息` → 订阅 **`im.message.receive_v1`**

---

## 4. 发布版本

进入应用 → 「版本管理与发布」→ 创建版本 → 申请发布。

**权限和事件订阅的改动必须发新版本才生效**，改了权限没发版是最常见的
「明明配了却收不到消息」的原因。

## 5. 试一下

私聊 bot 发 `/help`，应该收到命令列表。

然后直接问就行：

```
现在金价多少？
```

或者贴一条飞书云文档链接。**共享给机器人的文档无需任何授权**，直接就能读；
要读你自己账号下别的文档，先发 `/login` 授权一次：

```text
https://xxx.feishu.cn/docx/xxxxxxxx  帮我总结这份文档
```

「共享给机器人」的做法：在飞书里打开那份文档 → 右上角「···」→「添加文档应用」→
选这个应用；要让它能**写**（多维表格加记录 / 表格写单元格 / 文档追加正文），
共享时权限勾「可编辑」。

## 排错顺序

从下往上查，每一步都排除掉一大类问题：

| 现象 | 先查什么 |
|---|---|
| 飞书后台保存请求地址失败 | 部署是否成功；`/feishu-webhook` 路径对不对；挑战握手是否被验签挡掉 |
| 飞书后台推送日志显示超时/失败 | `INTERNAL_TOKEN` 配了吗（没配 webhook 会返 503）；agent 路由是否可达 |
| 收到消息但 bot 不回 | agent 的日志；`FEISHU_APP_SECRET` 对不对（取 token 会 401） |
| bot 回「没答上来：…」 | 模型路由。先打 `?probe=model`（见 `docs/03` 的「诊断探针」），它会直接告诉你 401 还是 400 |
| 卡片没有打字机效果，只有纯文本 | 正常 —— 卡片权限没配。见第 2 节 |
| 同一条消息被回答两次 | 去重失效。检查是不是同一个 conversation_id 被路由到了两个实例（见 `docs/01` 第二节） |
| 过一阵再问，之前的对话「忘了」 | 会话记忆是平台托管的、按会话隔离；`/clear` 会主动清空。想跨会话保留的事实要让它 `remember_fact` 记进长期记忆 |
| 贴了云文档链接，说读不了 | 文档没共享给机器人（右键「···」→ 添加文档应用）；或发 `/login` 走用户身份；也可能是链接类型不认（只支持 docx / wiki / sheets / bitable） |

## 环境变量清单（Makers 控制台）

```
# ── 模型路由 ─────────────────────────────────────────────────────────
# ⚠️ 用 OPENCODE_* 这组名字，**不要**用 AI_GATEWAY_*。
# 后者是平台托管的：每次 deploy 都会被 CLI 的
# `Bound AI Gateway credentials to project` 覆盖回平台值 ——
# 实测 setEnvs 写成功、listEnvs 回读一致，部署完就变回旧值。
# 曾经因此卡了很久，还一度误判成「setEnvs 改不了 AI_GATEWAY_*」。
OPENCODE_API_KEY         OpenCode Go 的密钥（sk-…）
OPENCODE_BASE_URL        https://opencode.ai/zen/go/v1
OPENCODE_MODEL           deepseek-v4.1-flash   ← 裸名，**不带** @makers/
OPENCODE_SESSION         edgeone-agent-lab     ← x-opencode-session 头的值

# key 和 baseURL 必须**成对**配。只配一半会被当成没配、退回 AI_GATEWAY_*，
# 于是又出现「key 是 A 家的、地址是 B 家的」这种 401。见 resolveModelRoute()。

FEISHU_APP_ID            cli_xxx
FEISHU_APP_SECRET        xxx
FEISHU_VERIFICATION_TOKEN xxx
FEISHU_ENCRYPT_KEY       xxx（建议配）

INTERNAL_TOKEN           openssl rand -hex 24   ← 必配，否则拒绝服务

FEISHU_DISPATCH_MODE     async（默认）｜ sync
SANDBOX_ENABLED          1（默认）｜ 0

# ── 工作区仓库（ws_ls / ws_read / ws_write / ws_rm，可选）──────────────
# 配了才挂这族工具。fine-grained PAT，只授 guci314/cf-agent-workspace 的
# Contents: Read and write。⚠️ 普通环境变量，别用 AI_GATEWAY_*（会被 deploy 覆盖）。
GITHUB_WORKSPACE_TOKEN    github_pat_…
GITHUB_WORKSPACE_REPO     默认 guci314/cf-agent-workspace，一般不用配

# 平台托管、会被 deploy 重置，仅作兜底，不要手改：
# AI_GATEWAY_API_KEY / AI_GATEWAY_BASE_URL / AI_GATEWAY_MODEL
```

可选：`FEISHU_ALLOWED_OPEN_IDS`（逗号分隔白名单，空 = 不限制）、
`AGENT_URL`（覆盖转发目标，默认同项目 `/feishu`）。

本地调试用 `edgeone makers link` 把控制台的环境变量同步到 `.env`。
