## 第 2 步 · 【未知数 1】后台执行能力 ⭐ 最关键

在状态页点「**跑一次自测**」按钮。它做两件事：

1. `POST /feishu?probe=start` → 立刻返回，后台睡 15 秒后写标记
2. 等 16 秒 → `POST /feishu?probe=check` → 读标记

**预期结果 A（✅ 后台可用）**：

```json
{
  "phase": "finished",
  "verdict": "✅ 后台执行可用 —— 用默认的 FEISHU_DISPATCH_MODE=async"
}
```

→ `FEISHU_DISPATCH_MODE` 保持 `async`。

**预期结果 B（❌ 后台不可用）**：

```json
{
  "phase": "started",
  "verdict": "❌ 后台任务没跑完（响应发出后进程被回收了）—— 把 FEISHU_DISPATCH_MODE 改成 sync"
}
```

→ 把 `FEISHU_DISPATCH_MODE` 改成 `sync`，重新部署。

**为什么要 15 秒**：太短的话任务可能在响应发出之前就跑完了，测出来的是
「同步能跑」而不是「后台能跑」—— 假的通过。

命令行等价做法：

```bash
CID=probe-abc123

curl --noproxy '*' -s -X POST "http://localhost:8088/feishu?probe=start" \
  -H "Makers-Conversation-Id: $CID"

sleep 16

curl --noproxy '*' -s -X POST "http://localhost:8088/feishu?probe=check" \
  -H "Makers-Conversation-Id: $CID"
```

## 第 5 步 · 真实飞书链路

1. 配好 `FEISHU_ENCRYPT_KEY`（现在该配上了）
2. 按 `docs/02-飞书配置.md` 走完飞书后台配置，**记得发版本**
3. 私聊 bot：

| 发什么 | 预期 |
|---|---|
| `/help` | 收到命令列表 |
| `/status` | 「还没有导入仓库。发 `/repo owner/name` …」 |
| `/repo sindresorhus/is-stream` | 先「正在抓取 …」，再「已导入 …N 个文件」 |
| `/status` | 显示仓库名、文件数、语料大小 |
| `这个包是怎么判断一个对象是不是 stream 的？` | 基于实际代码回答，带 `路径:行号` |
| 再发一次**同样**的问题 | 正常回答（不同 message_id，不该被去重） |
| `/compact` | 「已压缩：N 条历史 → 摘要（约 M 字）」 |
| 压缩后问 `我们刚才聊了什么` | **能从摘要答出**（这条是压缩的关键验收：答不出说明写回的形状不对） |
| `/clear` | 「会话已清空…」 |
| 清空后问 `我们聊过什么` | 回答没有历史；但 `/status` 里**仓库还在** |
| 空会话上发 `/compact` | 「只有 N 项历史，没什么可压缩的」 |
| `/memory` | 还没记过东西时，说明「记忆是空的，可以让我记 …」，**不是一片空白** |
| 说 `记住：这个项目用 pnpm 和 TypeScript` | 回复里应出现「记下了：…」（便于当场纠正） |
| `/memory` | 列出 `prefs/技术栈`（或模型自己起的键名） |
| `/forget 技术栈` | 「已忘记 …」。**不带 `prefs/` 前缀也要能删掉** |
| `/forget 不存在的键` | 直说找不到，不是静默成功 |

4. **验去重**：在飞书后台的推送日志里点「重新推送」同一条消息 ——
   bot 不该再回答一次。

5. **验自环防护**：bot 发「正在抓取…」这类回执时，
   那条回执自己会作为事件推回来 —— 不该触发新一轮对话。

### 验跨会话记忆（这一层的验收必须**换一个会话**）

`context.store.state` 是按会话隔离的，所以「在同一个群里记得」**证明不了**跨会话记忆生效 ——
那可能只是平台自己的会话状态。真正的验收是**换一个 conversation_id**：

| 步骤 | 预期 |
|---|---|
| 在群 A 说 `记住：这个项目用 pnpm`，确认回「记下了」 | ✅ |
| **私聊 bot**（不同 chat_id → 不同 conversation_id）问 `这个项目用什么包管理器` | **答得出 pnpm** ← 这条才是关键 |
| 在群 A 发 `/clear`，再问 `这个项目用什么包管理器` | **仍然答得出**（`/clear` 只清对话历史，不动长期记忆） |
| 私聊发 `/memory` | 看得到群 A 记的项目级事实；**看不到别人的按人记忆** |

> 如果第 2 条答不出，先打 `?probe=store` 看 Blob 后端在不在 ——
> 记忆功能在后端拿不到时会**整体静默关闭**（不挂工具、提示词也不提），
> 表现就是「bot 完全不知道自己有记忆」，而不是报错。

## 第 6 步 · 部署

推到 Git 仓库让 Makers 自动构建，或：

```bash
npm run deploy
```

⚠️ **两个部署的坑（都实测踩过）**：

1. **`deploy` 后面不要带路径参数**。`edgeone makers deploy .` 会跳过本地构建、
   把整个源码目录直接打包上传，平台侧重装依赖再构建，产物很容易超过
   「单文件 25MiB」限制（实测 30MiB 被拒）。`npm run deploy` 不带路径，
   CLI 会本地构建进 `.edgeone/` 并只上传构建产物（平台日志显示
   `Project only contains .edgeone directory, skipping build` 才是对的）。
2. **部署前删掉项目根的 `edgeone-agent-lab.zip`**。CLI 部署时会在项目根生成
   这个打包 zip，而它的静态资源收集不认识 `.zip`（默认只排除
   `node_modules/.cache/.git/.DS_Store/*.log/*.tmp`），下一轮构建会把它当
   静态文件收进 `.edgeone/assets/` → 31MiB 超限，从此每次部署都失败。
   `npm run deploy` 已把 `clean:zip` 串在前面。
3. **构建卡在 `Pre-build hook triggered` 不动，要 `env -u NODE_OPTIONS` 跑**。
   症状：日志停在

   ```
   🔍 [Logger Plugin] Pre-build hook triggered
   📂 Working directory: /Users/guci/work/edgeone-agent-lab
   ```

   然后十几二十分钟没有新输出，`.edgeone/` 的 mtime 也不动。
   原因不是网络也不是构建慢，而是环境里注入的 safe-delete shim
   （通过 `NODE_OPTIONS=--require=.../node-language-shim.cjs`）在构建清理
   `.edgeone/`（上万个文件）时弹 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，
   非交互模式下没人确认，就**一直挂着**。

   正确写法（`dangerouslyDisableSandbox` 单独用不够，shim 还在 NODE_OPTIONS 里）：

   ```bash
   env -u NODE_OPTIONS npm run deploy
   ```

   顺带把代理变量也摘掉（`-u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy -u ALL_PROXY -u all_proxy`），
   免得本机代理失效时把 CLI 的请求也带走。

⚠️ **部署会重置 `AI_GATEWAY_*`**。日志里那行
`[cli] Bound AI Gateway credentials to project ...` 就是它干的 ——
这三个键会被平台值覆盖。自定义模型配置放 `OPENCODE_*`。

**部署后要重跑第 2 步**（`https://<域名>/feishu?probe=start` / `?check`）——
线上的实例回收策略可能和本地不一样，本地通过不代表线上通过。

## 诊断探针（部署后随时可用）

排查「bot 不回 / 答不上来」时，**不要靠发飞书消息试**——一轮十几秒，
而且只能看到被包装过的错误文案。直接打探针，每一层单独测。

除 `start` / `check` 外，其余探针都要带 `token=<INTERNAL_TOKEN>`（这几个端点是公网可达的）；
`start` / `check` 不挡令牌是**故意的** —— 状态页要在浏览器里直接点它们，
把令牌塞进静态页等于公开它。所有探针都**必须带 `Makers-Conversation-Id` 头**，
否则平台先回 400。

```bash
BASE=https://eolab.yujizi.org/feishu
TOK=<INTERNAL_TOKEN>
CID=probe-diag-0001        # 任意 6~36 位 [0-9a-zA-Z-_.]
h=(-H "Makers-Conversation-Id: $CID")

curl -s "${h[@]}" "$BASE?probe=env&token=$TOK"    | python3 -m json.tool
curl -s "${h[@]}" "$BASE?probe=model&token=$TOK"  | python3 -m json.tool
curl -s "${h[@]}" "$BASE?probe=search&token=$TOK" | python3 -m json.tool
curl -s "${h[@]}" "$BASE?probe=store&token=$TOK"  | python3 -m json.tool
```

| 探针 | 测的是哪一层 | 看什么 |
|---|---|---|
| `?probe=env` | 环境变量**读到了没有** | **`envSource`（第一个看这个）**、`baseUrl`、`model`、`opencodeSession`、`managedAiGateway` |
| `?probe=model` | 模型请求**发得出去吗** | `upstream` 是哪个网关、`envSource`；200 就是通 |
| `?probe=search` | 运行时**出网**吗 | serper 的原始状态码和结果标题 |
| `?probe=store` | **跨会话存储**在不在 | **`memory.available` 和 `memory.reason`（第一个看这个）**、`runtime.getStoreType`、`storageEnv.PAGES_BLOB_DEPLOY_CREDENTIAL.isUnreplacedPlaceholder` |

> `memory.reason` 把「记忆为什么不见了」直接说成人话 —— 只有两种病：
> 运行时没暴露 `getStore`（平台改了 API），或者拿不到 projectId。
> 它和真实回合走的是**同一个解析函数**（`memoryBackendStatus`），
> 所以这个字段说 available 就是真 available。
> 顺带看 `memory.projectIdFrom` —— 能告诉你到底是 `env.PAGES_PROJECT_ID`
> 还是 `process.env.ProjectId` 生效了（这两个是不同来源，排查时容易混）。

`?probe=store` 还有一个跨会话的实测用法（**要换一个 conversation_id**）：

```bash
# 会话 A 写
curl -s -H "Makers-Conversation-Id: probe-a-0001" \
  "$BASE?probe=store&op=write&token=$TOK" | python3 -m json.tool

# 会话 B 读 —— blob.foreignCount > 0 就证明裸 Blob 跨会话可见
curl -s -H "Makers-Conversation-Id: probe-b-0002" \
  "$BASE?probe=store&op=read&token=$TOK" | python3 -m json.tool
```

写入都在 `probe-*` 前缀下，不碰 `repo.snapshot` / `feishu.*` 那些真键，也不碰
平台的 `memory-<projectId>` 里任何非探针键。

**为什么 `env` 和 `model` 要分开**：`env` 只证明变量读到了，不证明请求发得出去。
这两个探针各自对应一类完全不同的病：

| 探针结果 | 病在哪 |
|---|---|
| `envSource` 是 `AI_GATEWAY_*` | **路由退回了兜底**：`OPENCODE_*` 没配全。这是最常见的一种 |
| `env` 里 `baseUrl` 是 `ai-gateway.edgeone.link` | 同上，或者 `OPENCODE_*` 被删了 |
| `model` 401 `API key not found` | **打错门**：key 是 A 家的，baseURL 指着 B 家 |
| `model` 400 `provider prefix` | 模型名规则不对（EdgeOne 要 `@makers/`，OpenCode 要裸名） |
| `model` 429 / `QUOTA_EXHAUSTED` | 额度 |
| `model` 200 但 `search` 失败 | 模型没问题，查 serper key / 出网 |
| 两个都 200 但 bot 还是答不上来 | 才轮到看提示词和工具描述 |

⚠️ **`AI_GATEWAY_*` 是平台托管的，改不动**。每次 `edgeone makers deploy` 都会
`Bound AI Gateway credentials to project`，把这三个键覆盖回平台值。
所以自定义的模型配置必须放在 `OPENCODE_*` 这类普通键里。
`managedAiGateway` 字段就是用来看「它是不是又被重置了」。

⚠️ 加新环境变量时，记得同步 `probeEnv` 里的过滤正则
（`/FEISHU|INTERNAL|AI_|AGENT|SANDBOX|SERPER|OPENCODE/`）。
漏一个就会让那个变量在探针里**隐身**——曾经漏了 `SERPER`，
误判成「环境变量没生效」，白排查了半天。

## 一张表：出问题先看哪

| 现象 | 去哪看 |
|---|---|
| 类型错误 | 第 0 步的 `npm run typecheck` |
| 路由 404 | 文件位置：`agents/feishu/index.ts` → `/feishu`，`cloud-functions/feishu-webhook/index.ts` → `/feishu-webhook` |
| 401 内部令牌不匹配 | `INTERNAL_TOKEN` 在 webhook 和 agent 两边是不是同一个 |
| 503 没有配置 INTERNAL_TOKEN | 环境变量没配。这是**故意的** fail-closed |
| 400 缺少 Makers-Conversation-Id | webhook 的转发头没带上，或直接访问了 `/feishu` |
| 飞书收不到任何回复 | 第 5 步的排错顺序表 |
| bot 回「没答上来：…」 | 先打 `?probe=model`。200 才轮到查提示词 |
| 搜索不生效 | `?probe=model` 和 `?probe=search` 各打一次，分清是模型层还是工具层 |
| 回答和仓库无关 | 语料没导入成功 —— 发 `/status` 看文件数 |
| 换了群 / 换个人就「不记得」 | 先打 `?probe=store` 确认后端在；再看渲染的权限过滤（`user/*` 只注入提问人自己的） |
| bot 完全不知道自己有记忆 | **后端拿不到时功能整体静默关闭**（不挂工具、提示词也不提）。看 `?probe=store` 的 `runtime.getStoreType` |
| `/memory` 回「拿不到持久存储」 | 同上。这是设计如此，不是 bug |
| 记忆写不进去了 | 撞了 `MAX_ENTRIES = 100`。提示词里应让模型先 `forget_fact` 再记 |
| 卡片一直停在「生成中」 | 卡片权限没配，或 `closeStreaming` 失败。`streamer.finish()` 里已吞掉异常，不影响已显示的内容 |
