# 01 · 架构与移植映射

这份文档记录**每一处改动的理由**，以及**哪些保证变弱了**。移植最容易出问题的
不是「代码写不出来」，而是「照抄了代码但没照抄它依赖的平台保证」。

> `/repo` 命令和整个 `src/workspace/` 语料层已删除。本文档里凡是提到
> `workspace/` / 语料 / `generation` 制的地方，都是在讲**原版或移植时**的状态，
> 已在原处标注。删除的理由和完整清单见**第七节第 5 条**。

## 一、平台能力对照

| 能力 | Cloudflare（原版） | EdgeOne Makers（现在） | 差距 |
|---|---|---|---|
| 有状态计算单元 | Durable Object | `agents/` 会话模式 | 等价 |
| 按名字取实例、调方法 | `getAgentByName(env.ChatAgent, name)` 原生 RPC | ❌ **没有** | **硬缺口** |
| 会话身份 | URL 路径里的实例名 | `Makers-Conversation-Id` 请求头 | 载体变了 |
| 强一致 SQL | `ctx.storage.sql`（每实例一个 SQLite） | ❌ **没有** | **硬缺口** |
| 按会话隔离的 KV | 自己建表 | `context.store.state`（JSON KV） | 等价，但弱一致 |
| **跨会话共享的存储** | 自己建表（DO SQLite / KV） | **Blob**（agents 运行时内置 `getStore`） | 等价，但**无 CAS**；见第五节 |
| 对话记忆 | `agents/sessions` + `cf_agents_session_messages` 表 | `context.store.openaiSession()` | 等价，但**没有压缩钩子** |
| 延迟作业 / 重试 | `this.schedule()`（storage + alarm，自带退避重试） | ❌ **没有 alarm** | **硬缺口** |
| 定时任务 | Cron Triggers（最小 1 分钟） | cron-tick（免费版**最小 1 天**） | 免费版基本不可用 |
| 代码沙箱 | 自建（Judge0 / 阿里云 FC 云沙箱） | `context.tools.*` 内置 14 个工具 | **更强** |
| 单次执行上限 | 30 秒（Worker）/ DO 可配 | `agents/` 最长 3600 秒 | 更强 |
| 静态资源 | `env.ASSETS` | 项目根目录自动托管 | 等价 |

三个「硬缺口」里，两个（无 RPC 寻址、无 SQL）用别的机制绕过去了，
第三个（无 alarm）**没绕过去，只是换了个做法**，而且那个做法依赖一个未实测的
平台行为 —— 见下面第六节。

## 二、为什么拆成两段

### 硬约束

EdgeOne 官方文档原文：

> 统一用请求头 `Makers-Conversation-Id` 传递（**所有** `agents/*` 调用都要带）……
> 请求头缺失或不合法时，Agent 路由会返回 `400`。

而飞书的事件推送是**飞书服务器发起的**，我们没法给它加自定义请求头。

所以 `agents/` 路由**不可能**直接当飞书回调地址。必须有一个能做转发的中间层，
而这个中间层自己不能用 `agents/`（否则同样要那个头）。

### 于是

```
飞书 ──POST──▶ cloud-functions/feishu-webhook   （无状态，自己补头）
                      │
                      └──POST /feishu + Makers-Conversation-Id ──▶ agents/feishu
```

### ⚠️ 一个会静默 400 的坑：conversation_id 长度

原版用 `fs-${chatId}` 当实例名。照抄到 EdgeOne 会**全线 400**：

| | 值 | 长度 |
|---|---|---|
| 飞书 chat_id 实际形状 | `oc_` + 32 位十六进制 | **35** |
| 原版拼法 | `fs-` + 上面那串 | **38** |
| EdgeOne 上限 | 6 ~ 36 字符，仅 `0-9 a-z A-Z - _ .` | **36** |

超限。而且本地测试用短 id 时一切正常，线上真实会话全挂。

所以 `cloud-functions/feishu-webhook/index.ts` 里改成了哈希：

```ts
fs- + SHA-256(chatId) 的前 32 位十六进制   // 恒为 35 字符
```

哈希是**确定性**的，同一个 chat 永远映射到同一个 conversation_id —— 这是粘性
路由能成立的前提，不能换成随机 id。

### 为什么转发用 HTTP 而不是别的

`cloud-functions/` 拿到的 `context` 只有 `request / env / agent.store`，**没有**
任何「调用某个 agent」的能力。`context.agent.store` 是共享数据（读写对话消息），
不是调用入口。所以只能自己 `fetch` 同项目下的 agent 路由。

## 三、逐模块映射

### 保留不动（5 个文件，约 750 行）

这些文件零平台依赖，一行没改：

| `src/feishu/streamer.ts` | 只依赖 `card.ts` + `setInterval` |

### 微改（2 个文件）

**`src/feishu/turn.ts`** — 最初只改了一行：

```diff
- store.markDone(evt.messageId);          // DO SQLite 本地写，同步
+ await store.markDone(evt.messageId);    // KV 写，必须 await
```

顺带把 `FeishuQueueEvent` 的 import 从 `./router.ts` 改到 `./types.ts`
（router.ts 没移植）。

后来又加了 `/compact` `/clear` `/memory` `/forget` `/login` `/logout` 的分发；
2026-09-25 又删掉了 `case "repo"`（见第七节第 5 条）。

**`src/feishu/commands.ts`** — 原本一行没改，现在改过两处：

- 加了 `/compact` `/clear` `/memory` `/forget` `/login` `/logout` 及中文别名；
- 2026-09-25 删掉了 `/repo` / `/导入`，以及它依赖的 `OWNER_RE` / `REF_RE`。

> ⚠️ 删一个 `kind` 要连带删掉 `turn.ts` 里的 `case` —— TypeScript 的
> `switch` 要求 `case` 是联合成员，留着编译不过。这是好事：漏删会被编译器拦住。
> 真正的坑在**反方向** —— 如果顺手把 `default` 分支从 `{ kind: "error" }`
> 改成 `{ kind: "ask" }`，未知命令就会被当成普通提问送给模型即兴回答，
> 编译期完全看不出来。`test/smoke.ts` 里专门有一条端到端测试守这个。

### 重写（1 个文件）

#### `src/feishu/store.ts` — SQL → 按会话隔离的 JSON KV

原版两张表：`feishu_events`（去重 + 限流）、`feishu_token`（token 缓存）。

新后端用 `context.store.state`，它正好是「按 conversation_id 隔离的 JSON KV」——
而飞书这条路上「一个会话 = 一个 conversation_id = 一个 agent 实例」，
所以按会话隔离正好等价于原版「一个 DO 实例一个库」。

**接口从同步变成异步**，因为 KV 读写天生异步。原版的 `claim()` 能同步写，
是因为 DO 单线程 + 本地 SQLite 让「先查再写」天然原子。KV 没有这个保证，
所以改成 **进程内权威副本 + 写穿**：判定全在内存做（同步语义、天然原子），
改完整体写回 KV。

> **保证弱化的地方（重要）**
> 这套方案只在「同一时刻只有一个实例在处理这个会话」时正确。
> EdgeOne 的会话粘性路由给了这个保证。但它**不是分布式锁** ——
> 哪天同一个 conversation_id 被路由到两个实例，去重会失效，
> 表现为同一条消息被回答两次。原版的 DO 天然没这个问题。
>
> 要恢复强保证：把 `StateKv` 换成外部 MySQL/PG（`edgeone.json` 里
> `framework` 不变，在 `cloud-functions/` 里建连接），加唯一索引。
> `StateKv` 接口只有三个方法，换起来是局部改动。

另外加了两个原版没有的保护：`MAX_EVENTS = 500`（数组条数上限）和
写回时顺带 prune。原版靠 DO alarm 定期清理；EdgeOne 免费版 cron 最小间隔
是 1 天，所以改成「每轮对话跑完搭车 prune 一次」（`agents/feishu/index.ts` 里）。

> 原版还有第二张「重写」的表 —— `src/workspace/repo.ts`（语料仓储，SQL →
> 内存索引 + 快照）。**2026-09-25 随整个 `src/workspace/` 一起删掉了**，
> 见第七节第 5 条。

### 新增：云文档工具族（`src/feishu/docs.ts`）

原版没有这一族，是移植时新写的：7 个工具读写飞书云文档（读 3 + 写 3 + 建 1），
**应用身份优先、用户身份兜底**（`callDoc`）—— 共享给机器人的文档零授权可读，
没有共享的文档在提问人 `/login` 过之后用他自己的身份读。

#### ⚠️ `feishu_docx_write` 从写完起就是坏的（2026-09-25 用真实凭证才发现）

追加段落时，`block_type: 2`（文本）的载荷字段名是 **`text`**，而代码里写的是
**`paragraph`** —— 那是**旧版 `/docs/` API** 的字段名。飞书对字段名不认识时只回
一个光秃秃的 `1770001 invalid param`，不说哪个字段，所以照着错误码根本查不出来。

**它为什么能一直没被发现**：冒烟测试的断言写的是
`body.children[0].paragraph.elements[0].text_run.content` —— **把 bug 抄成了期望值**。
测试全绿，因为测试和实现出自同一个错误的认知。这跟「本地能跑通」是同一类假信号：
stub 能挡住「发出去的形状不对」，但**前提是期望值本身来自真实响应/文档，
而不是来自刚写完的实现**。

修法是把字段名改成 `text`，并加一条断言显式钉住 `!('paragraph' in block)`。

#### 2026-09-25 补的第七个工具：`feishu_docx_create`

补之前 7 个里没有一个是「建」——**全都要求一个已存在的资源链接**（`start(url)` 解出的
token）。于是「写一份报告」「建个会议纪要」这类请求全做不了，用户必须先自己建好文档、
共享给机器人、再把链接发过来。这个缺口是 agent 自己在工作区仓库里报的
（`reports/bug-feishu-docx-create.md`）。

实测确认的几件事（都是打真实 API 得到的，不是读文档推的）：

| 事实 | 怎么验的 |
|---|---|
| 应用身份**已经有**创建权限 | 发一个标题 2000 字的请求，回来的是 `99992402 field validation`（参数错）而不是 `99991672 Access denied`（权限错）—— 网关先查权限后校验参数，所以参数错就等于权限通 |
| 创建接口**只收 title** | 同一个响应里 `title` 是唯一被校验的字段，没有 content 入口 → 正文只能建完再追加 |
| 标题上限就是 **800** | 同上，`the max len is 800` |
| **应用身份建的文档：用户能打开，但只有只读** | 建了一篇，再用浏览器**以用户身份**打开：正常渲染、正文读得到；但菜单里是「申请编辑权限」、点「删除」回「无权限操作」、往正文里打字**打不进去** |

最后一条**推翻了一半**。原先担心的是「应用身份建的文档落在应用自己的云空间、
用户看不到，所以创建必须走用户身份、还得多要求一次 `/login`」—— 用户其实
**看得到**，所以没有为了「可见性」去改身份顺序。

但它翻出来的另一半是**新的、而且没解决**：用户拿到的是**只读**文档，
既改不了也删不掉。所以「创建走用户身份」这个选项**并没有因此失去理由** ——
用户身份建的文档落在他自己名下，可编辑、可删除。当前实现沿用应用优先，
代价就是**用户拿到一份自己改不了、也没人删得掉的报告**。

⚠️ **这是一个未决的取舍，不是结论**，别当成已经想清楚了：

- **应用优先**（现在的做法）：零门槛，不需要 `/login`；但产出只读，
  且**没有任何一方删得掉**（应用缺 scope、用户缺权限 —— 实测点删除回「无权限操作」）
- **用户优先**：产出归用户、可编辑可删；但没 `/login` 的人用不了这个工具

> 这里的两次「实测推翻推断」发生在**同一个 API 行为**上，方向还**相反** ——
> 第一次以为「用户看不到」（实际看得到），第二次才发现「用户能编辑」（实际只读）。
> 同一件事推理连错两次，说明「文档归谁、谁有权干什么」这类问题，
> **只能打一次真实 API + 用真人身份把 UI 上的每个操作真点一遍**才能确认；
> 读文档不够，推理更不够（两次我都很确信）。

**刻意不给删除能力（2026-09-25 决定）**：应用没有 `drive:drive` /
`space:document:delete`，所以**建出来的文档删不掉也移不动**（调 delete 回
`99991672` 要求这两个 scope 之一）。

⚠️ **「由人去飞书里清」这条路是走不通的**（实测 2026-09-25）：应用建的文档，
用户打开是**只读**，菜单里点「删除」回 `无权限操作` —— 所以**两边都删不掉**，
不打开 scope 就真的清不了。删文档的 API 是有的
（`DELETE /drive/v1/files/{token}?type=docx`，进回收站），卡点只在 scope。

⚠️ **这是有意的取舍，不是漏配** —— 别看到「机器人建了文档却删不掉」就去控制台
把 scope 开上。删除是不可逆的破坏性操作，而 `docs.ts` 里其它破坏性能力也是同一个
规矩（平台工具 `files_remove` 就是因此不挂的，见第八节）。要重新评估的话，
先想清楚「模型在什么条件下才该删、删错了谁赔」，再谈权限。

## 四、存储：原版的表都去哪了

原版 cf-agent-lab 里有 20 多张表（自己建的 + `agents` SDK 建的 +
`@cloudflare/ai-chat` 建的）。逐类去向：

| 原版表 | 用途 | 现在的去向 |
|---|---|---|
| `feishu_events` | 去重 / 限流 | `context.store.state` 的 `feishu.events` 键 |
| `feishu_token` | tenant_access_token 缓存 | `context.store.state` 的 `feishu.token` 键 |

| `cf_agents_session_messages` | **对话消息本体** | 平台托管，不暴露表名 |
| `cf_agents_session_compactions` | 会话压缩记录 | 手动的 `/compact`（见第七节第 1 条），**不是自动触发** |

原版不用管的（对话消息、调度记录），EdgeOne 也不让管。

## 五、跨会话记忆（2026-09-25 加）

原版的记忆有两层：**对话历史**（按实例隔离）和**跨会话的持久事实**（DO 的 SQLite）。
移植时只搬了第一层 —— `context.store.state` 的物理键是
`state/<conversation_id>/<key>`，**按会话隔离**。

这对对话历史是对的：每个群、每个人的私聊各聊各的。但「这个团队用 pnpm」
「谷词负责 auth 模块」这类**事实**不属于任何一个会话 ——
换个群就得重说一遍，`/clear` 之后就没了。

所以补了这一层。落点是 **Blob**，不是 `context.store`。

### 为什么是 Blob：一条实测链

官方文档的存储对照表里**没有 agents 运行时**（Blob 一栏只列了 Edge Functions /
Cloud Functions）。按文档推，agents 里想要持久存储只能绕道 Cloud Function 中转。
**实测推翻了这条推断**：

| # | 怎么测的 | 结果 |
|---|---|---|
| 1 | 读构建产物 `.edgeone/agent-node/server.mjs` | 运行时把 `globalThis.__EDGEONE_AGENT_RUNTIME__` 挂出来，7 个键，含 `getStore` |
| 2 | 用 CLI 令牌 + `ProjectId` 走 Blob 的 token 模式 | set / get / list / 1MB 值全通过；**换一个进程能读回上一个进程写的值** |
| 3 | 在裸 Node 里 `import server.mjs` | 那 7 个键都在，`getStore` 是函数，`PAGES_BLOB_DEPLOY_CREDENTIAL` 已注入且不是占位符 |
| 4 | 用平台自己的命名空间 `memory-<projectId>` 做 list | 255 个键，`state/<cid>/<key>` 的布局清晰可见 |

第 4 条是**不需要部署的证明**：平台自己的会话状态就躺在 Blob 里，
那 255 个键只可能是用环境里的凭证写进去的 —— 说明 agents 运行时确实有可用的 Blob 凭证。

凭证是**构建期注入**的，两条路径：生产替换 `{{PAGES_BLOB_DEPLOY_CREDENTIAL}}`
占位符；本地 dev 用 CLI 自己的令牌顶成 `DEV_BLOB_TOKEN` + `DEV_BLOB_PROJECT_ID`。
两种情况代码都只要 `getStore({ name })`，不用自己管凭证。

> ⚠️ 顺带纠正一条我自己早先写错的推断：曾经以为 `context.store` 是
> `createBlobBackedStore(blob, "agent-store", ...)`。实测 `agent-store`
> **这个命名空间根本不存在** —— 那个包装器只在别的路由形态下用，agents 路由没走它。

### 物理落盘：腾讯云 COS，且我们写的值**没有信封**

用同一个凭证在本地直连读 `agent-memory-<projectId>`，实测（2026-09-25）：

| 看什么 | 结果 |
|---|---|
| 响应头 `server` | `tencent-cos` |
| `x-cos-storage-class` | `MAZ_STANDARD`（多 AZ 标准存储） |
| `x-cos-version-id` / `x-cos-request-id` | 都有 —— 底层是 COS，不是自研 KV |
| `content-type` | `text/plain;charset=UTF-8` |
| `eo-cache-status` | 有（EdgeOne CDN 在前面；`eventual` 走 CDN，`strong` 走 no-cache 域名） |

**关键差异：我们写进去的值是「原样」的，平台不再包一层。**
同一个凭证下对比两个命名空间：

| 命名空间 | 读出来是什么 |
|---|---|
| `memory-<projectId>`（平台的） | `{"__eo_pages_store_v":…, "value":…, "expiresAt":…, "updatedAt":…}` |
| `agent-memory-<projectId>`（我们的） | 我们写的那个字符串，一个字节没变 |

原因是我们走的是**裸 SDK**（`getStore({name})`），而不是
`createBlobBackedStore()` —— 信封、TTL（`expiresAt`）都是那层包装器加的。
这带来一个好处和一个代价：好处是**键不会自己过期**，代价是没有 TTL 兜底，
增长只能靠 `MAX_ENTRIES` 管（见下面的弱保证）。

键名也是**原样**落盘，包括中文：`prefs/格式探针` 读回来就是 `prefs/格式探针`，
斜杠就是普通字符，不是真目录（`list` 返回 `{key, etag}` 两项，没有层级）。

### 隔离靠命名空间，不靠自觉

平台用 `memory-<projectId>`，里面是**线上用户数据**（对话消息、消息索引、状态）。
我们**不往里面加键**，另开一个 `agent-memory-<projectId>`。

理由不是洁癖：`list` 是按前缀枚举的。只要共用命名空间，任何一次前缀写错
都可能枚举到用户消息、或者一次清理删掉平台的键。分开之后，
这类事故在结构上不可能发生 —— `global-memory.ts` 里任何一个
`list` / `read` / `delete` 都碰不到平台的键。

### 一条事实一个键

Blob 的 `set` 是**整值覆盖，没有任何可用的条件写**。所以键空间按「一条事实一个键」铺：

```
prefs/<key>             项目级（技术栈、代码风格、团队约定）
user/<openId>/<key>     按人（「谷词负责 auth 模块」）
```

好处是两个会话同时记**不同**的事不会互相覆盖；搞成一个大 JSON 的话，
并发写就是丢数据。代价是渲染时要 `list` + 并行 `get` —— 只发生在每轮提问
开头一次，边缘节点毫秒级返回，实测可接受。

> ⚠️ **「一个 key 装一件事」这条规则必须写在 `remember_fact` 的工具描述里。**
> 实测（2026-09-25）：它原先只存在于 `global-memory.ts` 的文件头注释里 ——
> 那是给读代码的人看的，**模型看不到**。于是模型把「内部代号」和「发布分支」
> 并成了一个 key `prefs/项目代号与发布分支`；换个跑法又拆成两个。行为不稳定，
> 而并 key 恰恰把上面那句「不丢更新」的保证丢掉了。
>
> 这是同一个坑的第二次：`decisions.md` 当初也由 `init_memory` 创建、
> 却没有任何提示词提到它，实测两次真实运行模型都从没建过那个文件。
> **教训：提示词没说的规则，模型不会遵守。** 凡是希望模型照做的约束，
> 都必须落在模型看得见的地方（工具描述、`description`、字段说明、系统提示词），
> 写进代码注释等于没写。现在这条规则写在工具描述 + `key` 字段说明里，
> 并有冒烟测试钉住它不被重构删掉。

> ⚠️ 「没有条件写」这句是**实测**的，而且过程有点绕（2026-09-25）：
> SDK 的类型定义里**有** `SetOptions.onlyIfNew`，注释写着「only write if the key
> does not already exist」，还配了个 `PreconditionFailedError` —— 看着就是
> 现成的 CAS。**但实测它不生效**：键已存在时带 `onlyIfNew` 写照样覆盖成功。
> 底层 COS 其实有版本号（响应头 `x-cos-version-id`）和 etag，
> 只是 SDK 没暴露 `if-match` 这类参数，从这一层用不上。
> 所以**别信这个字段**，设计上不能依赖任何条件写。（ambient 模式没测，
> 但既然 token 模式不生效，就不能把它当地基。）
>
> 另一个实测结论：`set` **没有 TTL 参数**（`SetOptions` 只有 `onlyIfNew` /
> `cacheControl`），所以这些键不会自己过期。平台自己那层的 `expiresAt` 是
> `createBlobBackedStore` 包出来的，我们走裸 SDK 没有它 ——
> 「长期记忆」是真的长期，代价是增长只能靠 `MAX_ENTRIES` 兜。

`user/<openId>/` 这一层同时是**权限边界**：渲染时只注入 `prefs/*` 和
`user/<提问人>/*`，别人的按人记忆既不进提示词，`/memory` 列表里也只报条数、
不显示内容。

> ⚠️ **2026-09-25 评审修的**：上面那句原先只描述了「读进提示词」和 `/memory`
> 两处，而这条边界实际有**四个**入口 —— 模型手上还有 `recall_facts`（列全量）
> 和 `forget_fact`（删一条）。这两处当时**没有过滤**：群聊里任何人问一句
> 「把长期记忆列出来」就能拿到别人的个人事实内容，也能让 bot 把别人的记忆删掉。
>
> 根因不是漏看，是**实现散了**：可见性在 `renderForPrompt` / `renderMemoryList` /
> `forgetAll` 里各写了一遍，也各配了一条测试 —— 三份实现 + 三条测试看着覆盖得很全，
> 第四个入口就没人想起。现在收口成 `isVisibleTo(key, openId)` 一个纯函数，
> 四条路径（含 `forgetLoose` 那条手打键名的路）全部过它，测试也补上了。
>
> 教训：**权限边界要在收口处实现一次，不是在每个展示点各实现一遍。**
> 判断有没有漏的办法是数「有几个入口能读到/改到它」，不是数「写了几个过滤」。

### 记忆怎么进出

| 入口 | 谁用 | 做什么 |
|---|---|---|
| `remember_fact` | 模型 | 写一条。`scope` 选 `project` / `user`；同键再写是**更新** |
| `forget_fact` | 模型 | 删一条 |
| `recall_facts` | 模型 | 列出来看 |
| `/memory`（`/记忆`） | 人 | 看当前记了什么 |
| `/forget <键名>`（`/忘记`） | 人 | 删一条；键名可以不带 `prefs/` 前缀，`/forget all confirm` 清空 |

注入方式是把渲染结果**拼在系统提示词后面**，而不是塞进对话历史：
`Agent.instructions` 在 `@openai/agents` 里接受
`(runContext, agent) => Promise<string>`。
塞进历史的话会污染 `session`，而 `/compact` 又要把历史当历史来摘要。

### ⚠️ `instructions` 传函数时，**一次模型调用求值一次**（不是一轮一次）

这条是线上实测踩出来的，代价是机器人当众自我否定。

`@openai/agents-core/dist/run.mjs` 的 `#prepareModelCall` 里有一行
`await executionAgent.getSystemPrompt(...)`，而 `#prepareModelCall` 在**一轮的
轮次循环里被反复调用**（每一轮模型往返一次）。所以：

- 一轮里模型调几次工具，系统提示词就重新渲染几次；
- 记忆一变（`remember_fact` 写过），**同一个系统提示词在一轮之内会变** ——
  前一次是「（目前还是空的）」，后一次列出了刚写的两条。

实测的坏结果（2026-09-25，真实飞书链路）：模型先调 `recall_facts`（那时记忆确实空，
返回 0 条 —— **合法**），然后 `remember_fact` 写了两条；下一次模型调用时提示词里
已经有了这两条。模型同时看到「提示词里有 2 条」和「工具说 0 条」，
判定成「我的读取不稳定」，接着**在飞书里撤回一个正确的答案**，
下一轮又撤回上一条撤回。用户看到的是「它反复横跳、不可信」——
这比记不住更伤。

**修法**：`_host.ts` 里把渲染结果**按轮快照**（`memoryText()` 闭包 memo），
提示词在一轮内保持稳定；「现在到底有什么」交给 `recall_facts`。
职责分开之后两者不会再互相打脸。

同时给提示词补了两条读数规则（`_instructions.ts`）：清单是**本轮快照**、
`recall_facts` 是**实时**，不一致时以 `recall_facts` 为准；
并且明确禁止「反复更正/撤回自己」。

> 排查过程值得记一笔：一开始怀疑是 Blob 的 `list` 有写后读滞后，
> 于是先测存储层（写一条立刻 list，连做 3 轮 + 反复复现）——
> **完全一致，没有滞后**；再用真实代码 + 真实 Blob 复现 4 种调用顺序，
> 全部正确。存储和代码都没问题，问题在「提示词会变」这件事上。
> **先证伪自己的第一假设，再去读 SDK 源码**，比直接改代码省事得多。

**拿不到 Blob 后端时整个功能自动消失**：不挂那三个工具，提示词里也不提记忆，
`/memory` 直说「这次运行拿不到持久存储」。**刻意不用内存实现兜底** ——
一个「这一轮记得、下一条消息就忘了」的记忆比没有记忆更坏，
用户会以为记下了。

> ⚠️ 「静默关闭」这个设计有个代价：**出问题时没有任何报错**，表现只是
> 「bot 完全不知道自己有记忆」。所以配了 `memoryBackendStatus()` ——
> `?probe=store` 的 `memory` 字段就是它的输出，和真实回合用的是同一个解析函数。
> 它把病因直接说成人话（运行时没暴露 `getStore` / 拿不到 projectId），
> 还报 `projectIdFrom` 说明到底是 `env.PAGES_PROJECT_ID` 还是
> `process.env.ProjectId` 生效了。
>
> projectId 之所以要**两处都找**：实测 agents 运行时把 Blob 凭证
> （`PAGES_BLOB_DEPLOY_CREDENTIAL`）注入在 `process.env`，
> 只查 `context.env` 有整个功能静默失效的风险。

### 遗忘机制：硬上限 + 让模型自己取舍

无上限的记忆会一直长，最后把上下文撑爆。所以：

- `MAX_ENTRIES = 100`：记满之后 `remember_fact` **拒绝写入**，并告诉模型先删。
  比默默丢最老的更可控 —— 哪条还有用只有模型知道。
- `MAX_VALUE_CHARS = 500`：单条上限。事实不是文档，超了说明该拆。
- 渲染预算：最多 30 条 / 3000 字符，超了按条截断**并说明还有多少没显示**。
  不说明的话模型会以为自己看到了全部。

### ⚠️ 这套方案的弱保证

1. **没有条件写**。两个会话同时写**同一个键**，后写的赢。对「偏好」这类语义是
   合适的（最后说的算），但别拿它当需要精确累加的地方用。
   连「不存在才写」都没有 —— SDK 的 `onlyIfNew` 实测不生效（见上）。
2. **最终一致**。Blob 是最终一致的，我们读的时候显式要 `consistency: "strong"`，
   但那只是「读到已提交的值」，不是线性一致。
3. **上限是软的**。`MAX_ENTRIES` 只在 `remember` 时检查，而且「先查再写」在并发下
   可能同时判成新键，能轻微突破它（渲染预算兜住了后果）。
4. **键不会过期**。`set` 没有 TTL 参数，所以「记错了一条忘了删」会一直在，
   并且每轮都注入提示词。这是 `MAX_ENTRIES` 存在的第二个理由。

## 六、调度：`schedule()` + alarm → 202 + 后台

这是移植里**唯一没真正解决、只是换了做法**的地方。

### 原版怎么做的

```ts
// webhook 立刻 ACK，工作交给 DO 的 alarm
await this.schedule(new Date(), "feishuRun", evt, {
  retry: { maxAttempts: 3, baseDelayMs: 500, maxDelayMs: 4000 },
});
```

原版注释里写清了为什么不用 `waitUntil()`：

> 用 `schedule()` 而非 `waitUntil()` 是因为后者绑在请求上，
> DO 被驱逐就静默丢失消息。

### EdgeOne 没有 alarm

免费版 cron 最小间隔 **1 天**，等于没有定时能力。

所以改成：**agent 先回 202，再在后台跑完整个回合**。

### ✅ 未知数一（已实测通过）：返回 Response 之后，未 await 的异步代码还能不能跑完

这是整套设计的地基，而**官方文档没有明文承诺**。

理论依据是有的：`agents/` 是会话模式，同一 conversation_id 粘性路由到同一实例，
实例在会话空闲 300 秒内保活。既然实例还在，事件循环就该继续转。
但「该」不等于「会」—— 有些运行时在响应发出后冻结事件循环。

**所以做了自测端点**：

```
POST /feishu?probe=start   → 立刻返回，后台睡 15 秒后写一个标记
POST /feishu?probe=check   → 读那个标记（隔 16 秒再发）
```

为什么是 15 秒而不是 1 秒：太短的话任务可能在响应发出**之前**就跑完了，
那样测出来的是「同步能跑」，是假的通过。

**2026-09-25 线上实测结果：✅ 成立。** `FEISHU_DISPATCH_MODE` 保持默认的 `async`：

```json
{"ok":true,"phase":"finished","elapsedMs":15046,
 "verdict":"✅ 后台执行可用 —— 用默认的 FEISHU_DISPATCH_MODE=async"}
```

`elapsedMs` 15046 ≈ 15 秒，说明那 15 秒的 sleep 确实是在**响应发出之后**才跑完的 ——
这正是要证的那件事。（如果运行时冻结了事件循环，`phase` 会一直是 `pending`。）

**万一实测是 ❌ 怎么办**：把 `FEISHU_DISPATCH_MODE` 改成 `sync`。
那时 agent 跑完才返回，webhook 跟着等 —— 飞书会在 3 秒后判超时并重推，
重推被 agent 的去重挡住，而回答本来就走 `sendText`/卡片发出去、不依赖
webhook 的响应体。所以用户体验仍然是「发消息 → 等一下 → bot 回复」，
只是飞书后台的推送日志里会有超时重试记录。

### ⚠️ 未知数二：流事件的名字

原版流式卡片靠 AI SDK 的 `onChunk({ chunk })`，`chunk.type` 只有四个值
（`reasoning-delta` / `text-delta` / `tool-input-start` / `tool-result`），很直白。

OpenAI Agents SDK 换成两层事件：`raw_model_stream_event`（模型原始分片）
和 `run_item_stream_event`（运行项）。我在 `agents/feishu/_host.ts` 的
`applyEvent()` 里处理了四个：

| 想要的效果 | 事件 | 确认程度 |
|---|---|---|
| 答案增量 | `raw_model_stream_event` + `data.type === 'output_text_delta'` | ✅ 官方模板里有 |
| 工具调用 | `run_item_stream_event` + `name === 'tool_called'` | ✅ 官方模板里有 |
| 工具结果 | `run_item_stream_event` + `name === 'tool_output'` | ⚠️ 按规律推的 |
| 思考增量 | `raw_model_stream_event` + `data.type === 'response.reasoning_*_delta'` | ⚠️ 按规律推的 |

后两个猜错的后果只是「卡片上少显示一行」，**不影响答案正确性** ——
因为最终答案优先取 `result.finalOutput`，不依赖增量。

核对方法：本地起服务后打开 `http://localhost:8088/agent-metrics`，
看真实事件名，对不上就改 `applyEvent()`。

## 七、丢了的能力

### 1. 会话压缩 —— 自动化那半仍然没有，改成了手动命令

原版：

```ts
this.sessions.session()
  .onCompaction(createCompactFunction({
    summarize: (prompt) => this.summarize(prompt),
    keepRecentTokens: 6_000,
  }))
  .compactAfter(200_000);   // 超过 20 万估算 token 就压缩
```

配合的模型是 100 万 token 窗口（`mimo-v2.5`），200k ≈ 用掉 20%，留足余量。

EdgeOne 的 `context.store.openaiSession()` 给的是 OpenAI Agents SDK 的原生
`Session` 实现（`getItems` / `addItems` / `popItem` / `clearSession`），
**没有暴露压缩钩子** —— 阈值触发这条自动路径没地方挂。

**现在改用两条手动命令补上**（2026-09-23 加）：

| 命令 | 做什么 |
|---|---|
| `/compact`（`/压缩`） | `getItems()` → 调模型生成摘要 → `clearSession()` → `addItems([摘要])` |
| `/clear`（`/清空`） | `clearSession()`，长期记忆（Blob）不动 |

实现（`src/feishu/compact.ts` + `agents/feishu/_host.ts`）：

- **摘要请求不走 `run(agent, …)`**，直接用同一个 OpenAI 客户端打一次
  Chat Completions。走 Agent run 的话这一回合会被写进 session，
  而压缩要求「读到全量历史 → 清空 → 只写回摘要」，中间插进别的项顺序就乱了。
  绕过 run 天然不污染历史，这是唯一干净的做法。
- 写回的形状是**一条 user message**，开头注明「以下是此前对话的压缩摘要：」，
  让后续轮次认得出这是历史而不是新指令。
- 少于 3 项历史时拒绝压缩（摘要不会比原文短），这顺带让 `/compact` 幂等 ——
  压完只剩一条摘要项，再发一次会被门槛挡住。
- 摘要为空时**不清 session**：宁可这次失败重来，也不能清完没东西写回。
- 历史渲染成文本是纯函数，放在 `src/feishu/compact.ts`（零依赖），
  `test/smoke.ts` 的 G 节直接测它 —— 和当初把宿主能力抽成接口是同一个动机。
- ⚠️ `SUMMARY_SYSTEM_PROMPT` 里列的「必须保留的四类信息」是**跟着助手定位走的**。
  2026-09-25 改通用助手时，原来那条「本会话导入过哪些仓库（owner/name@ref）」
  已经换成了「引用过的来源（URL / 云文档链接）」。**改定位时别漏了这个文件** ——
  它和 `_instructions.ts` 一样是提示词，只是住在 `src/` 里，很容易被忘掉。

**剩下的退化**：压不压缩由用户决定，不是自动的。连续问几十轮而想不起来发
`/compact` 的话，照样会撞上下文窗口。要补自动化，得放弃「用平台原生 Session」
这个选择：在 `_host.ts` 的 `ask()` 里自己读历史 + 拼 `input`，不再交给 `session`，
才能塞进「超过 N 条就先压一次」的判断。

### 2. GitHub 工作区工具（ws_ls / ws_read / ws_write / ws_rm）—— 2026-09-25 已移植

原版 `src/ghworkspace/`（670 行）提供「往 agent 自己的 GitHub 私有仓库里读写文件」
的能力，默认目标是 `guci314/cf-agent-workspace`。

移植时**刻意没搬**（当时的理由：要额外的 token 配置、平台 `files_*` 沙箱看起来够用），
后来按用户要求补上了：agent 无需用户任何授权就能读写这个仓库。最终搬法：

- `src/shared/base64.ts` —— 把 `sandbox/base64.ts` 那 78 行拷回 `shared/`（当初
  「依赖 sandbox 层所以搬不了」的理由随之消失）；
- `src/ghworkspace/client.ts` —— 纯逻辑**原样移植**，只改 import 和文件头
  （EdgeOne 侧的凭证是普通环境变量 `GITHUB_WORKSPACE_TOKEN`，⚠️ 别用 AI_GATEWAY_*，
  那三个键每次 deploy 都被平台覆盖）；
- `src/ghworkspace/tools.ts` —— 工具定义从 AI SDK 的 `jsonSchema` 换成
  `@openai/agents` 的 zod（本仓统一形状），返回**数组**而不是对象
  （`_host.ts` 统一展开）；业务逻辑一行没动。

挂载条件：`GITHUB_WORKSPACE_TOKEN` 配了才挂，没配一个工具都不挂（别挂一族
必然失败的工具让模型反复去撞）。提示词段落 `WORKSPACE_PROMPT` 也按同一条件拼接 ——
「说了但手上没有的能力，模型会去调然后白烧一轮」。

### 3. 网页聊天界面

原版有 React 前端（`src/client.tsx` + `src/workspace-panel.tsx` + 5 个组件），
还有 `/api/workspace/*` 那套浏览器导入协议（`src/workspace/routes.ts` +
`src/workspace/ingest.ts`）。

按用户的决定，**飞书是唯一入口**，所以这些全删了。仓库根目录只留一个
静态状态页（`index.html`），用来显示回调地址和跑后台执行自测。

### 4. `run_python` 的 `files` 参数

原版的 `run_python` 能把仓库里指定文件的内容一起送进沙箱。平台工具
（`code_interpreter` / `commands` / `files_write`）**没有这个联动**。

补救写进了系统提示词：让模型先把文件读出来、再写进沙箱或直接嵌进代码，
走两步。代价是多一轮工具调用，功能上不缺失。

### 5. 仓库语料层（`/repo` + 整个 `src/workspace/`）—— 2026-09-25 删

**这是后来主动删的，不是移植时就没搬。** 移植时 `src/workspace/` 是**搬过来了、
还跑通了**的：9 个文件（`repo` / `tools` / `github` / `tar` / `glob` / `filter` /
`decode` / `serve-ingest` / `types`），配 `/repo owner/name` 命令、快照持久化、
以及 `test/smoke.ts` 里两整节测试。

删掉的原因：**助手定位变了**。用户要的是「通用助手」，不是「问某个 GitHub 仓库」。
留着这套东西的代价不是几行代码，而是：

- 提示词里得同时照顾两种人格（「用户先导语料」和「手上什么都没有」），
  而这两者的工具集和行为规则是冲突的；
- `read` / `ls` / `grep` / `find` 这四个工具名和沙箱那族**语义重叠**，
  模型会在两套之间选错；
- 删掉之后「手上没有的语料」这件事不存在了，提示词能只说一件事。

删的范围（一次改完，两边仓库都改）：

| 删了什么 | 说明 |
|---|---|
| `src/workspace/` 9 个文件 | 整个目录 |
| `Command` 的 `repo` 成员 | 连带 `OWNER_RE` / `REF_RE` / `parseRepoArg` / `REPO_USAGE` |
| `turn.ts` 的 `case "repo"` | 不删编译不过（`case` 必须是联合成员） |
| `FeishuTurnHost.ingest()` | 接口从 3 个方法缩到 2 个 |
| `HostDeps.repo` + `makeSnapshotStore()` | `agents/feishu/index.ts` 里那套快照存储 |
| 提示词里的「怎么用这四个工具」 | `agents/feishu/_instructions.ts` |
| `compact.ts` 里的「导入过哪些仓库」 | 换成「引用过的来源」 |
| `test/smoke.ts` 的 E / F 两节 + `seed()` | 换成一条「`/repo` 已判成未知命令」的端到端测试 |

**⚠️ 删一层之前先看有没有别人在 import 它里面的通用零件。**
`src/workspace/tools.ts` 里住着 `guarded()`（工具永不抛的兜底），而
`src/feishu/docs.ts` 和 `agents/feishu/_search.ts` 都在用它。直接 `git rm` 会把
两个不相干的模块一起搞崩。做法是先把它抽到 `src/shared/util.ts`，改完 import，
再删目录。

**没删的**：长期记忆（`global-memory.ts`）、云文档工具族（`docs.ts`）、
会话压缩（`compact.ts`）、沙箱工具、webhook 转发 —— 这些和「问哪个仓库」无关。

## 八、沙箱：自建 → 平台内置

原版 `src/sandbox/` 有 1100 行（8 个文件），接了三条路：

| 原版路径 | 用途 | 现在的对应 |
|---|---|---|
| `judge0.ts` | 公共 Judge0 实例跑 Python | `code_interpreter` |
| `aliyun.ts` + `warm.ts` | 阿里云 FC 云沙箱，保温复用 | 平台按会话自动管沙箱（一对话一沙箱） |
| `executor.ts` | 自建执行器 | 同上 |
| `zip.ts` + `base64.ts` | 打包/编码辅助 | 不需要 |
| `tool.ts` | 工具定义 + 后端选择逻辑（416 行） | 不需要 |

平台内置 14 个工具，我们挂 **8 个**：

**挂**：`commands` `code_interpreter` `files_read` `files_write`
`files_list` `files_exists` `files_make_dir` `browser_fetch`

**不挂**（`agents/feishu/_tools.ts` 的 `EXCLUDED`）：
`browser_screenshot` `browser_click` `browser_type` `browser_evaluate` `files_remove`

`browser_*` 那四个是「点页面元素」的操作类工具：模型在飞书里答一个问题，
没机会跟人来回确认点击目标，挂了只会让它乱点一通。要读网页用 `browser_fetch`。
`files_remove` 不挂是因为它是个**破坏性操作**，而这条链路没有任何需要删文件的场景。

> ⚠️ **平台那个 `web_search` 也被摘掉了** —— 它是第 14 个、也是第 6 个被排除的。
> 原因是它底层依赖腾讯云 WSA，本项目没配 `WSA_API_KEY`，一调就报
> `web_search requires the WSA_API_KEY environment variable.`，**是坏的**。
> 我们自己挂了一个同名的（serper，见 `agents/feishu/_search.ts`），
> 名字故意保持一致，模型无需知道来源变了。所以
> `platformTools()` 有个 `extraExcluded` 参数：自建的挂上时把平台那个摘掉，
> 否则两个同名同用途的工具同时在列表里，模型选哪个全看运气。

`SANDBOX_ENABLED=0` 可以整条关掉（想先只跑通纯搜索问答时有用）。

| # | 未知数 | 怎么测 | 状态（2026-09-25） |

| 2 | 流事件的实际名字 | `http://localhost:8088/agent-metrics` 看真实事件 | ⚠️ **仍未核** —— 本地起不来 agent 路由（`agent-node` 不绑端口），要部署后从 metrics 看。猜错的后果只是卡片少一行，不影响答案 |

另外三处「按文档写、没实测」的，风险低但值得留意：

- **平台工具的实际名字**（`commands` / `code_interpreter` / …）——
  来自官方文档《Using the Agent Framework》的表。名字是模型选工具的唯一依据，
  写错等于工具不存在。`/agent-metrics` 里能看到实际注册了什么。
- **`context.tools.all()` 在 `openai-agents-sdk` 框架下返回的对象形状** ——
  文档说是「lightweight function-tool compatible object」，能直接塞进
  `Agent({ tools })`。`_tools.ts` 里按 `unknown[]` 收，不做形状假设。
- **`context.store.state` 的单值大小上限** —— 文档没给数字。
  现在存的最大的东西是 `feishu.events` 那 500 条去重记录（几十 KB 量级），
  离任何合理上限都很远。（2026-09-25 之前这里还存过 6MB 的语料快照，
  那条路已经删了。）

## 十、如果要恢复强保证

按投入从小到大：

1. **去重的强保证** —— 把 `StateKv` 换成外部 MySQL/PG，加
   `unique(message_id)` 索引。`store.ts` 里只有三处调用 KV，改动局部。
2. **会话压缩自动化** —— 手动的 `/compact` 已经有了（第七节第 1 条）；
   要让它自己按阈值触发，得放弃 `context.store.openaiSession()`、改成自己拼
   input。
3. **定时清理** —— 用 GitHub Actions（最小间隔 5 分钟）当外部调度器
   打一个清理端点，替代原版的 DO alarm。
4. **记忆的并发写** —— Blob 无 CAS，「同时写同一个键后写的赢」。要精确控制的话，
   把 `MemoryBackend` 换成外部 Redis/PG 加事务。接口只有 4 个方法
   （`put` / `read` / `remove` / `list`），换起来是局部改动 ——
   和 `StateKv` 一样是刻意留窄的缝。

> 原第 2 条「语料持久化」已经随 `src/workspace/` 一起删了（第七节第 5 条）。
> 那条曾经是这份文档里最复杂的移植点之一 —— `repo.snapshot` 的 6MB 上限、
> generation 制的原子切换、`fileCursor` 的惰性游标。**定位一变，整块复杂度直接归零**，
> 这本身就是删它的收益之一。
